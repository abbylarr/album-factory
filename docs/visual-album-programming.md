# Визуальное программирование альбома: разворот, данные, правила

26 сентября 2026 · развитие [UX-спецификации редактора](album-template-editor-ux.md)

Исходная идея и [экран в Figma](https://www.figma.com/design/cTIkKZnwLj1sBdLC8K25k6/Album-Factory?node-id=553-7624): рядом с обычными инструментами есть «авто текст» и «авто плейсхолдер». Автор рисует привычным способом, но может назначить элементу источник данных. На экране уже различимы миниатюры разворотов, холст и фото-рамка с подписью «Портрет». Это продуктовая концепция, а не описание реализованной функции.

Реализованная версия и ограничения: [редактор мастер-макета](master-editor.md). Далее — концепция дальнейшего развития.

## Главная формулировка

Фотограф **рисует не готовую страницу, а правило её создания**. Он видит пример с настоящими тестовыми данными и может в любой момент переключиться на другой состав класса или вариант ученика. Обычный слой остаётся статичным. Автоматический слой имеет источник, контекст, правило отсутствующих данных и область применения.

Два предложенных подхода соединяются:

- **Роль разворота** даёт безопасную структуру и определяет, какие данные здесь уместны: обложка, персональный разворот, учителя, виньетки, общие фото, финал.
- **Динамические элементы** позволяют создать собственное оформление внутри этой роли: текст, фото, повторяемая карточка, группа, условная видимость.

Так фотограф не пишет программу и не выбирает произвольный путь в базе. Он отвечает на вопросы интерфейса: «Что это за разворот?», «Для кого он?», «Что сюда подставить?», «Что делать, если данных нет?».

## Модель, которую видит автор

```text
Дизайн «Классика»
  ├─ Издание «Эконом»       → набор разделов, правила объёма, печать
  └─ Издание «Стандарт»     → другой набор и возможности, тот же визуальный язык

Каждое издание
  ├─ Обложка                → контекст варианта ученика/учителя
  ├─ Персональный разворот  → контекст одного ученика/учителя
  ├─ Учителя                → коллекция учителей заказа
  ├─ Наш класс              → коллекция учеников заказа
  └─ Общие фото             → фотографии, выбранные фотографом
```

**Дизайн** — визуальный язык и библиотека блоков. **Издание** — опубликованная программа сборки в определённом формате и с конкретной комплектацией. **Предложение фотографа** — коммерческое название и цена, связанные с изданием. Это сохраняет разделение из [модели каталога](domain-model-v2.md): «Эконом» и «Стандарт» могут иметь общую основу дизайна, но разные проверяемые издания. Изменение черновика дизайна не изменяет опубликованные версии и заказы.

## Три уровня автоматизации

### 1. Одно значение

Автор создаёт «Авто текст» или «Авто фото». На холсте появляется пример, справа — понятный выбор источника. Для персонального разворота: «Имя этого ученика», «Его цитата», «Выбранный портрет». Для обложки: «Класс», «Год выпуска», «Портрет владельца варианта». Для общего разворота: «Название школы», «Общая фотография». Внутри документа хранится устойчивый идентификатор роли, а не написанное на кнопке название.

У каждого элемента показываются **источник, пример, наличие данных, запасной вариант, право изменения в заказе**. Например: «Портрет владельца → клиентский выбор → если нет, предупредить → фотограф может заменить».

### 2. Повторить для списка

Автор собирает одну карточку: фото + имя + подпись. Выделяет группу и выбирает «Повторять для → Ученики». На холсте видит 20 карточек тестового класса. Свойства повторения: порядок, число колонок, промежутки, максимальное число на развороте, правило последней неполной страницы, переполнение на следующий разворот. У каждого повторения появляется локальный контекст «этот ученик»; текст «Имя этого ученика» и фото «Портрет этого ученика» остаются связаны с одной персоной.

Это важнее простого «авто плейсхолдера»: фотограф конструирует **один элемент и правило его тиражирования**, а система создаёт нужное число экземпляров.

### 3. Выбрать композицию по условию

Автор создаёт состояния одного раздела: «3–8 учеников», «9–18», «19–30» и т. д. или использует предложенные системой сетки. Он может настроить правила «если учителей нет — скрыть раздел», «если цитаты нет — убрать её блок», «если фото одно — использовать крупную композицию». Интерфейс показывает все возможные ветки и просит проверить их перед выпуском. Здесь появляется визуальная программа сборки, но без произвольного кода.

Этот уровень следует раскрывать после освоения первых двух. Иначе чистый лист с условиями превратится в конструктор, которым фотографу трудно пользоваться.

## Как автор выбирает источник данных

Не показывать таблицы базы, JSON-пути или длинный список всех полей. Сначала роль разворота задаёт **контекст**; затем меню предлагает подходящие значения по типу элемента.

| Роль | Контекст | Пример доступных источников |
|---|---|---|
| Обложка | владелец варианта + заказ | портрет владельца, имя, класс, школа, год |
| Персональный | текущий ученик/учитель + заказ | портрет, альтернативный портрет, имя, цитата, предмет |
| Учителя | список учителей заказа | карточка учителя: портрет, имя, предмет |
| Виньетки | список учеников заказа | карточка ученика: портрет, имя, цитата |
| Общие фото | заказ + отобранные фото | фото класса, групповое фото, подпись, школа |

Меню на правой панели может выглядеть так: **«Подставлять: [Имя ученика]» → «Источник: [Ученик этого варианта]» → «Когда пусто: [Скрыть подпись]»**. После выбора холст показывает реальные данные; значок связи и подсветка объясняют, почему элемент заполняется именно так. По нажатию на значок видна цепочка: «Анкета → выбранный ученик → имя → этот текст».

Если один слой должен брать данные из другой области, например портрет классного руководителя на обложку учительского варианта, это отдельный явный источник. Несовместимые поля не предлагаются; при смене роли разворота система показывает, какие связи требуют переназначения.

## Поведение на холсте

- Сверху обычные инструменты: выбор, текст, фото, фигура, перо; рядом — «Авто текст», «Авто фото», «Повторяемый блок». Роль разворота выбирается при его создании и всегда видна в заголовке.
- На холсте обычный режим показывает итоговый разворот. Переключатель «Показать связи» добавляет метки к динамическим элементам и подсвечивает границу повторяемой группы. Так результат не загромождён служебными значками.
- Клик по автоматическому элементу открывает справа **«Содержимое»**, **«Источник»**, **«Если пусто»**, **«Разрешить менять в заказе»** и обычные визуальные свойства.
- Внизу — «Проверить на»: выбор состава класса, конкретного ученика, отсутствующих цитат, разных учителей и набора фото. Автор может нажать «случай длинного имени» и сразу увидеть переполнение.
- В отдельном режиме «Программа» показан короткий порядок разделов и условия их появления. Это обзор, а не обязательный граф из десятков узлов.

## Пример: виньетки

1. Фотограф создаёт разворот и выбирает назначение **«Виньетки учеников»**.
2. Рисует одну карточку: фото-рамка, имя, декоративная линия.
3. Выделяет карточку → **«Повторять для всех учеников»**.
4. В рамке выбирает «Портрет этого ученика», в тексте — «Имя этого ученика».
5. Указывает сетку 4 × 3, отступы и правило переполнения.
6. Переключает тестовый класс с 12 на 26 учеников; система добавляет нужные страницы виньеток; фиксированные общие разделы сохраняют свой объём.

Именно этот сценарий отличает продукт от обычного графического редактора: одна визуальная карточка становится правилом для множества персональных документов.

## Что делать с отсутствующими и неоднозначными данными

- Обязательное фото не найдено → ошибка с указанием персоны, источника и места на холсте.
- Необязательная цитата пуста → скрыть блок, оставить пустое место или применить авторский текст; автор выбирает одно правило.
- Слишком длинное имя → заранее заданный минимум кегля; после него ошибка. Текст молча не обрезается.
- Несколько подходящих фото → правило выбора роли: клиентский выбор, назначение фотографом или ручное заполнение. «Любое фото» не годится для обязательного персонального портрета.
- Коллекция не помещается → повторить шаблон виньеток до включения всех участников; невозможная геометрия карточки блокирует экспорт, а не отбрасывает людей.

## Как развивать без чрезмерной сложности

**Первый рабочий шаг:** обязательные роли разворотов, свободное оформление, авто текст/фото с выбором источника, тестовые данные и проверка. Это «редактор шаблонов с привязкой», понятный большинству фотографов.

**Второй шаг:** повторяемая карточка для учеников и учителей, автоматическое распределение по разворотам. Это первая по-настоящему программируемая часть.

**Третий шаг:** несколько состояний композиции, условия видимости и варианты «Эконом / Стандарт» на общей библиотеке компонентов. Условия задаются из небольшого каталога, а не языком выражений.

**Дальше:** более общая платформа для каталогов, сертификатов, бейджей и других персонализированных печатных материалов возможна, если разделить нейтральный механизм «контекст → коллекция → элемент → правило» и предметные роли альбома. Проверять это расширение стоит после успешной работы с альбомами, чтобы не размыть первый продукт.

## Вопросы для проверки на прототипе

1. Понимает ли фотограф разницу между «фото на странице» и «фото каждого ученика» без объяснений?
2. Может ли он назначить имя и портрет одной карточке, затем увидеть 20 корректных карточек?
3. Находит ли он источник неправильного фото через метку на холсте?
4. Понимает ли, что «Эконом» и «Стандарт» — две опубликованные программы в одном дизайне, а цена живёт в предложении?
5. Может ли проверить 3, 20 и 54 ученика и исправить переполнение без обращения к разработчику?

Самое рискованное UX-место — не рисование слоёв, а объяснение **контекста и повторения**. Прототип надо начинать с персональной страницы и виньеток, а не с полной панели инструментов.
