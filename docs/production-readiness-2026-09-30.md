# Публичный запуск Album Factory: аудит и план

Дата: 30 сентября 2026. Масштаб первого запуска: 10–30 студий, подтверждён владельцем. Объём фото/день и требуемое время ожидания пока не заданы.

## Решение

Сохранить Python/FastAPI, модели компьютерного зрения, веб-редактор и бизнес-логику. Подготовить модульный сервис с отдельными процессами API, анализа и экспорта, PostgreSQL и закрытым S3-совместимым хранилищем. Для первого испытания — Linux x86-64, 8 vCPU с предсказуемой производительностью, 32 ГБ RAM, 100–200 ГБ SSD для системы и временных файлов. Это кандидат для нагрузочного теста, а не доказанная достаточная конфигурация для любого объёма 30 студий.

Публичный адрес сам по себе не делает сервис готовым. Главные блокеры: автоматический локальный вход, непроверенная полнота изоляции студий, общая очередь внутри API, синхронный экспорт, локальные пути и отсутствие проверенного восстановления.

## Что изучено и границы вывода

Проверены текущие файлы рабочей копии, включая незакоммиченные изменения: server.py, mvp.py, jobs.py, layout_queue.py, faces.py, sorting_v3.py, production_v3.py, vision.py, general_photos.py, general_meta.py, storage.py, uploads.py, layout_workspace.py, layout_render.py, production.py, school_catalog.py, master_templates.py, pyproject.toml и документация.

SQLite прочитан в режиме read-only/query-only; извлечены только агрегаты, без имён, контактов, фото и векторов лиц. Использованы сохранённые замеры и исторические испытания. Новый нагрузочный тест, аудит всех маршрутов, тест проникновения и замеры в облаке не выполнялись. Работающее приложение и его данные не изменялись. Этот документ — анализ, не реализация production.

## Блокеры до реальных публичных данных

### 1. Локальный вход и границы доступа — P0

`server.py:243–276` выдаёт посетителю главной страницы `album_session = app.state.token`, а `mvp.py:108` принимает его как студию `local`. Если просто разрешить публичный домен и открыть сервер, любой посетитель сможет получить права локальной студии. TrustedHost сейчас ограничивает localhost; эту защиту нельзя заменить на публичный домен, оставив автоматический вход.

Нужны явные режимы development/production. В production автоматическая выдача локальной сессии запрещена, незалогиненный API отвечает 401. Локальные заказы мигрируются в студию конкретного владельца. Отдельная тестовая среда использует искусственные фотографии и отдельные данные.

Для каждого ресурса проверять цепочку пользователь → студия → заказ/школа/дизайн → файл. UUID и неизвестный URL не заменяют авторизацию. Проверить фотографии, шрифты, мастер-ресурсы, PDF, ZIP, ссылки клиента, задания и статусы, массовые операции. Фоновому заданию передавать studio_id явно: ContextVar HTTP-запроса нельзя считать авторизацией отдельного процесса.

Критерий: студия B не может получить, изменить, удалить или экспортировать ресурсы A даже с известными ID; клиентский код одного заказа не открывает другой. Эти проверки должны стать интеграционными тестами.

### 2. Публичная аутентификация — P0

В `mvp.py:134` используется PBKDF2-HMAC-SHA256 с 50 000 итераций. Перейти на Argon2id либо настроенный по актуальным рекомендациям PBKDF2 с миграцией старых хешей при входе. OWASP рекомендует Argon2id; для PBKDF2-HMAC-SHA256 указывает 600 000 итераций в соответствующем варианте. [Рекомендации OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Cookies сейчас без Secure. Нужны HTTPS, Secure/HttpOnly/SameSite, выход и отзыв сессий, ограничения перебора входа и регистрации, безопасное восстановление доступа. Для закрытой беты допустимы приглашения и ручной административный процесс восстановления с проверкой владельца; для открытой регистрации нужны полноценные сценарии восстановления/подтверждения.

Проверку Origin сохранить и адаптировать к HTTPS-прокси: фиксированный публичный origin, корректная передача схемы/host и доверие forwarded-заголовкам только от своего прокси. БД и внутренние процессы недоступны из интернета.

PIN класса — осознанное право видеть/менять общий набор участников. Если родители должны видеть только своего ребёнка, нужны персональные приглашения и привязка к персоне. Общий PIN управления не даёт индивидуального аудита действий. Для беты можно сохранить общий кабинет только после принятия этой модели доступа. Ссылки должны отзываться; bearer-токены в URL исключить из логов и сторонней аналитики. PIN, сохраняемые для повторной отправки в `order_codes`, сейчас открытые: предусмотреть перевыпуск либо защищённое хранение с отдельным ключом.

### 3. Очереди и восстановление — P0

В `server.py:38,182` один ThreadPoolExecutor и общий worker_lock на все студии. Анализ запускается внутри процесса API. Очередь долговечна в SQLite, но вычислительная инфраструктура пока локальная. `process_pending` забирает всю текущую съёмку: большая съёмка задерживает чужие небольшие заказы. Учительские фотографии используют тот же executor.

`jobs.py:52` не имеет lease/heartbeat/владельца попытки; после гибели исполнителя running-задание может остаться навсегда. Повтор ошибки возвращает pending без задержки. `mvp.py:705–708` запускает export через run_once прямо из HTTP-обработчика. Это не независимый постоянно работающий экспортный worker. `layout_queue.py:33` строит макет внутри BEGIN IMMEDIATE и ждёт глобального завершения обработки в основном worker. Признак uploading управляется браузером: закрытие вкладки может оставить его установленным.

Целевая схема: API сохраняет операцию и возвращает job_id; отдельный worker выполняет задачу; интерфейс показывает прогресс/ошибку/повтор. Очереди анализа, макетов и тяжёлого экспорта получают отдельные лимиты. Задания содержат studio_id, order_id, input_revision, model_version, attempt, lease_until, heartbeat и ссылку на результат. Нужны timeout, backoff, восстановление зависших заданий, отмена, предел повторов и сигнал об окончательной ошибке.

На старте можно использовать PostgreSQL-очередь с атомарным захватом и `FOR UPDATE SKIP LOCKED`, lease и журналом. [PostgreSQL](https://www.postgresql.org/docs/current/sql-select.html) описывает SKIP LOCKED для конкурирующих потребителей очереди. Альтернатива — Celery и брокер, с долговечным состоянием в PostgreSQL и продуманной доставкой/повторами. Не требуется одновременно внедрять оба варианта. [FastAPI](https://fastapi.tiangolo.com/tutorial/background-tasks/) рекомендует отдельные инструменты для тяжёлых фоновых вычислений.

Задачи выполнять хотя бы один раз с идемпотентным результатом, а не обещать exactly-once. Применять результат только если входная версия актуальна. Обработку группировки V3 нельзя бездумно распараллелить по кадрам: она зависит от соседей и текущих групп. Сначала разделить независимые заказы между worker-процессами; внутри заказа сохранить порядок и блокировку. Ограниченные пакеты между студиями должны учитывать соседние кадры алгоритма. Для общего анализа отдельная финальная задача пересчитывает связи и серии после готовности зависимостей.

Нельзя просто добавить `uvicorn --workers 4`: каждый процесс создаст собственный executor, модели и локальные locks, а init_db сбрасывает processing при каждом запуске. Нужны независимый worker и координация через БД.

### 4. Хранение и загрузки — P0

Оригиналы, JPEG, миниатюры, ресурсы мастер-макетов, копии публикаций и экспорт живут на локальных путях. Переход к S3 потребует адаптера storage и изменения снимков: храним ключ объекта/версию/хеш вместо абсолютного пути ноутбука. Рендер получает ограниченный временный локальный кеш. Нельзя заменить только ALBUM_DATA_DIR на URL бакета.

Приватный бакет: API сначала проверяет права и выдаёт короткую подписанную ссылку либо отдаёт файл через авторизованный маршрут. Загружать можно прямо в объектное хранилище по ограниченной сессии; при завершении сервер проверяет размер, checksum, формат и владельца. Незавершённые загрузки имеют TTL. Оригиналы и опубликованные версии неизменяемы; повторная обработка создаёт новую версию производных.

Текущий основной upload (`server.py:619`) собирает весь файл в память; четыре image-worker не ограничивают количество HTTP-запросов, ожидающих обработки с байтами в памяти. Лимит 30 МБ и 50 Мп не заменяет лимиты одновременно принимаемых загрузок, памяти процесса и диска. При 50 Мп один RGB-буфер — около 150 МБ, копии/декодирование увеличивают расход.

Ввести квоты студии: байты, фото/заказ, число активных заданий, одновременные загрузки. У учительских фото отдельные квоты — они сейчас не входят в MAX_PHOTOS заказа. Проверять также растровый размер печати/DPI, число разворотов/вариантов, архивы и прочие импортируемые ресурсы. Декодеры/рендер запускать с ограничениями памяти, времени и временного диска.

### 5. БД, эксплуатация и данные — P0

SQLite с WAL пригодна для локальной разработки и ограниченного одноузлового пилота. Для публичных 10–30 независимых студий предлагается PostgreSQL: короткие транзакции, индексы, версионированные миграции, пул подключений, блокировки на уровне заказа. Это не простой поиск/замена SQL: используются PRAGMA, INSERT OR REPLACE, SQLite-специфические транзакции и init-функции в модулях.

Сборку закрепить полным lock-файлом, версиями моделей/checksum, контейнером и проверкой необходимых моделей при readiness. Частичный requirements-tested.txt не закрепляет все runtime-зависимости. Отсутствующие необязательные модели сейчас уменьшают набор функций; production должен сообщать об этом явно. Модели/кеш prompts подготовить в сборке, чтобы не скачивать их при первом клиентском запросе.

Нужны: HTTPS-домен и обратный прокси, автоматический restart, firewall, SSH по ключам, секреты вне репозитория, отдельные dev/staging/prod, проверка перед выпуском, rollback совместимый с миграциями. Метрики: длина/возраст очереди по типам и студиям, throughput, p50/p95 обработки и HTTP, ошибки/повторы, RAM/CPU, диск и стоимость хранения. Логи с request_id/job_id, без паролей/PIN/токенов/биометрических векторов.

Бэкап БД и объектов, отдельные права на удаление, версия/срок хранения, регулярное восстановление на пустой среде. Резервная копия на том же сервере не защищает от его потери. Для первой беты предлагаемые цели, которые ещё нужно подтвердить: RPO до 24 часов, RTO до 4 часов. Для оплачиваемого сервиса отдельно согласовать более строгие цели.

retention_deadline сейчас лишь вычисляет дату; это не планировщик удаления. Политику хранения привязать к завершению заказа/договору, предусмотреть активные заказы, портреты учителей, снимки публикаций, экспорты, эмбеддинги и сроки в резервных копиях. Не запускать безусловное удаление через 90 дней от создания заказа.

## Производительность: факты и неизвестные

### Сохранённые локальные измерения

В базе 2 947 готовых портретных фотографий. Для 2 896 кадров source=face: средний интервал 0,241 с, медиана 0,215 с, p95 0,396 с. Для 50 source=sequence: средний интервал 0,031 с. Ещё один manual. Сумма всех записанных интервалов — около 699 с, то есть 11,65 минуты; около 253 фото/мин, если суммировать эти интервалы. Это не измеренная длительность одной общей партии: записи могли относиться к разным запускам.

production_v3.py:14 записывает время между сохранениями результатов; оно включает часть работы БД и ожидания, но не загрузку, все финальные операции и инициализацию FaceEngine. Это wall-clock интервалы, не CPU-секунды. Не переводить их напрямую в требуемое количество CPU.

В исторических sorting_trials есть лабораторный V3 на 1 000 кадров: 66,66 и 61,23 с (примерно 900–980 фото/мин). Это исторические испытания другого пути, без доказательства полной эквивалентности текущему production-коду. В production есть дополнительное определение рамки лица через engine.frame, обращения к БД и повторный detector. Поэтому 1 000 фото за минуту нельзя обещать публичным пользователям.

Общих фото и замеров полного GeneralVision в текущей базе нет. Там выполняются лица/эмбеддинги, опциональные выражения, тела RTMO, CLIP-сцена и пересчёт связей/серий. Цена кадра зависит от числа лиц. RTMO/CLIP используют CPUExecutionProvider, а объект GeneralVision имеет lock. GPU автоматически не подключится. Настройка OpenCV/ONNX threads и числа процессов необходима: ONNX Runtime по умолчанию может использовать физические ядра в каждой сессии. [Документация ONNX Runtime](https://onnxruntime.ai/docs/performance/tune-performance/threading.html).

### Сценарии для 10–30 студий

Число студий не задаёт нагрузку само по себе. Если каждая загружает 1 000 фото в активный день, это 10–30 тысяч/день; если 3 000 — 30–90 тысяч/день. Это сценарии, не прогноз поведения пользователей. Важно, придут ли загрузки за восемь часов или одновременно за 15 минут.

Формула планирования: N = W × H × 3600 × U / t. W — независимые исполнители с достаточным CPU/RAM, H — окно обработки в часах, U — целевая загрузка (пример 0,6), t — измеренные секунды на кадр в смешанном потоке. При H=8, U=0,6 один исполнитель даёт 17 280 / t кадров за окно:

- t=0,5 с → 34 560 фото; 3 000 фото без очереди примерно 25 минут.
- t=1 с → 17 280 фото; 3 000 фото примерно 50 минут.
- t=2 с → 8 640 фото; 3 000 фото примерно 100 минут.
- t=5 с → 3 456 фото; 3 000 фото примерно 250 минут.

Все четыре t — входные предположения, не измеренная скорость облака. Для 30 000 фото при t=1 с нужно примерно два таких исполнителя на восьмичасовое окно, для 90 000 — шесть. При t=2 с нужно примерно четыре и одиннадцать. Умножение не гарантирует линейного ускорения на одном сервере: процессам требуются ядра, RAM и I/O.

Для смеси считать t = доля портретов × t_портрет + доля общих × t_общий с отдельным бюджетом загрузки/финализации/экспорта. Даже небольшая доля медленного общего анализа может определять всю очередь. При большой вспышке загрузок учитывать время ожидания до старта, не только секунды обработки кадра.

### Автовёрстка и печать

Раскладка документа вероятно легче полного анализа, но это ещё не измерено. build_layout выполняется внутри транзакции; большие варианты и подбор общих фото способны задерживать запись. Генерировать по снимку вне долгой write-транзакции, затем коротко проверять версию и сохранять результат.

PDF/JPEG/ZIP считать отдельной тяжёлой нагрузкой. export_print_files растеризует каждый разворот через PDFium в 300 DPI; персональные варианты умножают число разворотов, декодированных изображений и выходных файлов. _Images хранит кеш кропов. Экспорт сейчас запускается и из HTTP. Нужны отдельный процесс, лимит конкурентных экспортов (начать с одного), измерение пиков RAM и кеш по revision. Готовое скачивание должно только отдавать файл.

## Размер хранения

По файлам data/photos: 2 954 оригинала — 3,107 ГБ; 2 954 рабочих JPEG — 2,857 ГБ; миниатюры — 0,066 ГБ. Суммарно 6,03 ГБ, около 2,04 МБ/фото. Количество файлов отличается от строк photos; причины различия в этом аудите не расследовались. Публикации, учителя, PDF/ZIP и бэкапы сюда не включены.

При 30 тысячах фото/день и 90 днях хранения это около 5,5 ТБ только трёх вариантов фото; при 90 тысячах — около 16,5 ТБ. Если реальные оригиналы по 10 МБ, а рабочий JPEG такой же, один кадр занимает уже около 20 МБ; 30 тысяч/день за 90 дней — около 54 ТБ. Календарная частота съёмок может снизить объём, но её пока не знаем.

Отдельно измерять трафик: 30 тысяч оригиналов по 10 МБ — 300 ГБ входящих данных/день. На линии 100 Мбит/с идеальная передача этого объёма занимает около 6,7 часа; реальная дольше. Прямые загрузки в S3 снимают этот поток с API, но не отменяют лимиты и тарификацию хранилища.

## Какой сервер выбрать

Для закрытой демонстрации с искусственными данными можно использовать 4 vCPU/16 ГБ и ограниченную очередь. Для заявленного старта с реальными независимыми студиями — испытать 8 vCPU/32 ГБ, 100–200 ГБ SSD, x86-64 Linux, без GPU. Первоначально API, worker и PostgreSQL могут жить на одной VM в отдельных контейнерах с лимитами; это единая точка отказа. Более устойчивый вариант — API/БД отдельно от вычислительного worker, managed PostgreSQL с бэкапами. На worker-node 8 vCPU/32 ГБ количество исполнителей определяется тестом, а не числом ядер в названии тарифа.

Оригиналы с первого публичного запуска — в приватном объектном хранилище с возможностью роста до ТБ; локальный SSD — временный буфер. Не покупать GPU и Kubernetes до измерений. При росте первым добавлять вычислительные узлы для анализа и экспорта; бизнес-логику не требуется разбивать на сеть микросервисов.

Кандидаты в российском регионе: Selectel и Yandex Cloud. Selectel предлагает выделенные CPU-ядра для предсказуемой нагрузки; vCPU при SMT не равно физическому ядру. [Описание Selectel](https://docs.selectel.ru/cloud-servers/about/dedicated-cores/). Сравнивать одинаковые CPU/RAM, регион, гарантию CPU, SSD, сеть и поддержку. [Калькулятор Selectel](https://selectel.ru/prices/), [тарификация Yandex Compute](https://yandex.cloud/ru/docs/compute/pricing).

Полный месячный бюджет: VM + PostgreSQL/его диск + S3 объём + операции S3 + исходящий трафик + бэкап + IP + мониторинг + эксплуатация. Тарифы меняются, окончательная смета требует объёма фото, retention и трафика; здесь не приводится неподтверждённая цена готовой конфигурации. Object Storage тарифицирует не только объём. [Тарификация Yandex Object Storage](https://yandex.cloud/ru/docs/storage/pricing).

## Правила работы с реальными фотографиями

Поскольку первый рынок — Россия, архитектурно выбрать размещение первичных данных, анализа и резервных копий в РФ. Статья 18 ч. 5 152-ФЗ ограничивает использование зарубежных баз при сборе ПД граждан РФ с предусмотренными исключениями. [Текст статьи 18](https://www.consultant.ru/document/cons_doc_LAW_61801/cbf4e15b7c330f9372e876cdf2bc928bad7950ef/).

Перед реальными заказами определить роль студии и сервиса в обработке, основания обработки, документы/согласия представителей детей, поручение обработки, уведомление РКН с учётом применимых исключений, права доступа, срок удаления и порядок инцидентов. [Статья 22](https://www.consultant.ru/document/cons_doc_LAW_61801/d996966e22e1320c9de1ab82d9f6be12c3d9d765/).

Сервис создаёт векторы лиц и сопоставляет их с персонами. Это требует отдельной юридической оценки применимости режима биометрических ПД; нельзя считать все фотографии биометрией автоматически или исключать этот режим лишь потому, что нет входа по лицу. Статья 11 связывает режим с характеристиками человека и использованием для установления личности. [Статья 11](https://www.consultant.ru/document/cons_doc_LAW_61801/7336c78762a98b5f4f698b8c3800dca1111acc16/). Это вопрос к специалисту по ПД с описанием реального алгоритма и целей, а не подтверждение соответствия сервиса закону этим аудитом.

## Последовательность реализации

1. Закрыть локальный вход в production; завершить кабинет студии и модель доступа класса; провести межстудийные тесты всех ресурсов. Результат: безопасный вход, отзыв доступа, отсутствие доступа к чужим данным.
2. Выделить DB/storage interfaces, внедрить PostgreSQL и миграции; перенести обезличенный тестовый заказ и проверить полный цикл. Результат: приложение без путей ноутбука, воспроизводимая миграция.
3. Выделить независимые worker-процессы, долговечные задания/leases, очередь по студиям и отдельный экспорт. Результат: перезапуск API не прерывает worker, гибель worker не теряет задачу, повтор не портит результат.
4. Подключить приватный S3, квоты/TTL/версии/политику удаления и ограниченный временный кеш. Результат: загрузка/просмотр/экспорт работают на чистом сервере, без публичных оригиналов.
5. Собрать контейнеры, прокси/HTTPS, staging, секреты, мониторинг, бэкап/восстановление и rollback. Результат: развёртывание на пустой среде по инструкции.
6. Прогнать нагрузку, уточнить сервер и стоимость, согласовать документы для реальных данных. Начать закрытую бету с несколькими приглашёнными студиями; расширять до 10–30 по наблюдаемой очереди и ошибкам.

Безопасное публичное демо с синтетическими данными возможно раньше полного SaaS. Публичная бета с реальными детскими фотографиями требует выполнения P0. Оплачиваемая production-версия дополнительно требует согласованных SLA, полноценной поддержки/восстановления и правил оплаты, если оплата входит в запуск.

## Испытание перед покупкой постоянной конфигурации

- Одинаковая репрезентативная выборка: 1 000 портретов, 300 общих кадров с разным числом лиц, реальные разрешения/сжатие; только разрешённые к такой обработке данные. Проверить полный набор моделей, прогрев и холодный старт.
- По отдельности измерить загрузку/производные, face extract/frame, общий analyze, refresh/series, build_layout, PDF и печатный JPEG/ZIP; затем полный поток. Метрики: wall time всей партии, фото/мин, p50/p95, пиковая RSS каждого процесса/контейнера, CPU, диск, ошибки, доля ручной проверки.
- Сравнить 1/2/4 worker-процесса и лимиты ONNX/OpenCV threads при фиксированных ресурсах; сохранить качество группировки, а не только скорость.
- Нагрузка API: 10 и 30 параллельных студий, загрузки и клиентские просмотры одновременно с одним тяжёлым экспортом; отдельный всплеск 30 × 3 000 фото. Проверить квоты и справедливость очереди.
- Принудительно остановить worker, перезапустить API, повторить загрузку/экспорт, имитировать недоступность S3/БД и нехватку диска. Доказать восстановление без двойного результата и вечных processing/running.
- Предлагаемые критерии беты: обычные запросы API p95 до 1 с под тестовой нагрузкой; безопасный отказ по квотам вместо OOM; статус/прогресс доступен; задачи восстанавливаются после lease timeout; чужой доступ всегда отклоняется; восстановление бэкапа укладывается в принятые RPO/RTO. Время анализа партии согласовать после замера.

Постоянный тариф и обещание «N фотографий в день» выбирать только после этих испытаний. На текущих данных доказана работоспособность локальных портретов, но не пропускная способность полного публичного сервиса.
